# calendar

## Purpose
Renders the GitHub contribution calendar across several years as flat, GitHub-style year grids. GitHub's
`contributionsCollection` only covers a one-year window, so the plugin walks each year in roughly four-week
chunks aligned on Sundays, concatenates the returned weeks and emits one entry per year, newest first.

## Key Files
| File | Description |
|------|-------------|
| `index.mjs` | Computes the year range from `plugin_calendar_limit` and `data.user.createdAt`, then loops `for (let year = start; year <= end; year++)` and inside each year walks `from`/`to` windows (`to.setUTCHours(+4 * 7 * 24)`, snapped back to the previous Sunday with `to.setUTCHours(-to.getUTCDay() * 24)`, clamped to the end of the year or to now). Each window's end is pushed back to 23:59:59.999 of the previous day so ranges never overlap. Years are `unshift`ed so the newest year comes first. |
| `metadata.yml` | `category: github`, `index: 17`, `supports: user` only, `scopes: public_access`. Two inputs: `plugin_calendar` and `plugin_calendar_limit` (default 1; `n > 0` shows the last `n` years, `0` shows everything since registration, `n < 0` extends `n` years before registration for accounts with pre-GitHub commit history). |
| `examples.yml` | Two examples: current year, and full history with `plugin_calendar_limit: 0`. |
| `README.md` | GENERATED by `npm run build`. Never hand-edit. |

## Skipped subdirectories
- `queries/` — no AGENTS.md: `setup.mjs` loads every file in it as a GraphQL query. Contents:
  - `calendar.graphql` (`CalendarDefault`, `$login`, `$from`, `$to`) — the contribution calendar for a date
    range: `weeks { contributionDays { contributionCount color date } }`. **This file is currently unused.**
    `index.mjs` calls `queries.isocalendar.calendar(...)`, and the two files are byte-for-byte equivalent apart
    from the query name. The mock `tests/mocks/api/github/graphql/calendar.default.mjs` exists for it and is
    likewise never hit; `isocalendar.calendar.mjs` is what answers in practice. Deleting the file would remove
    `queries.calendar` entirely, so fix it by switching `index.mjs` to `queries.calendar()` rather than by
    deleting.

## For AI Agents
### Working In This Directory
- The year loop issues roughly 13 GraphQL requests per year (one per four-week window), all sequential. With
  `plugin_calendar_limit: 0` on an old account this is the most request-hungry part of a render; keep that in
  mind before widening the window or adding fields.
- Boundary arithmetic is deliberate: windows must start on a Sunday for GitHub to return aligned weeks, and the
  `dto` copy (previous day at 23:59:59.999) prevents a duplicated week at each seam. Changing either produces
  duplicated or missing columns rather than an error.
- Only `data.user.createdAt` is needed from `base`, so the plugin works with a minimal base fetch, but it does
  not work token-less.
- `supports: user` means the `repository` template is skipped for this plugin's test cases and the plugin
  throws `Unsupported context` if invoked for an organization.
- The `--halloween` and `--winter` debug flags in `core/index.mjs` rewrite `data.plugins.calendar.years[].weeks[].contributionDays[].color`
  after this plugin resolves, so the `color` field must stay a plain string.
- `README.md` is generated; edit `metadata.yml` / `examples.yml` and run `npm run build`.

### Testing Requirements
- `npm run test-metrics` runs `tests/cases/calendar.plugin.yml` for `classic` only (`calendar.ejs` exists only
  in `source/templates/classic/partials/`, and `supports:` excludes `repository`).
- Mock actually used: `tests/mocks/api/github/graphql/isocalendar.calendar.mjs` (because of the
  `queries.isocalendar.calendar` call). `calendar.default.mjs` is present but unreachable.
- Rendered by `source/templates/classic/partials/calendar.ejs`.

### Common Patterns
- Result shape: `{years: [{year, weeks: [{contributionDays: [{contributionCount, color, date}]}]}]}`.
- Date windows are built with `setUTCHours` arithmetic on cloned `Date` objects rather than a date library.
- Standard plugin skeleton: early `return null` on `!q.calendar` or a failed `enabled()` check, everything else
  inside `try {} catch (error) { throw imports.format.error(error) }`.
