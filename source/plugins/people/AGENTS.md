# people

## Purpose
Renders avatar grids for the accounts related to a user, organization or repository: followers, following,
sponsors, sponsored accounts, organization members, repository contributors, stargazers, watchers, and a
manual "thanks" list. It switches between a user/organization context and a repository context depending on
whether the query targets a repository, and each section is fetched with a different query or REST endpoint.

## Skipped subdirectories
- `queries/` - no AGENTS.md: `setup.mjs` `load.plugin` reads every file in it as a GraphQL query string.
  Contents:
  - `people.graphql` (`query PeopleDefault`) - pages one relation of an account, returning `login` and
    `avatarUrl(size:)` per edge. Variables: `$account` (`user` or `organization`), `$login`, `$type` (the
    relation field name, for example `followers`, `following`, `membersWithRole`), `$after`
    (pre-rendered `after: "<cursor>"` or empty), `$size`.
  - `repository.graphql` (`query PeopleRepository`) - same shape nested under `repository(name: "$repository")`,
    used for `stargazers` and `watchers`. Variables: `$account`, `$login` (repository owner), `$repository`,
    `$type`, `$after`, `$size`.
  - `sponsors.graphql` (`query PeopleSponsors`) - pages `sponsorshipsAsMaintainer` or `sponsorshipsAsSponsor`
    and unwraps the sponsorship node through a `$target` field with an inline `... on User` fragment.
    Variables: `$account`, `$login`, `$type`, `$after`, `$size`, `$target` (`sponsorEntity` for maintainers,
    `sponsorable` for sponsors).

## For AI Agents
### Working In This Directory
- Allowed types are context-dependent and silently filtered, so an unsupported value produces an empty
  section rather than an error. User accounts allow `followers`, `following`, `sponsorshipsAsMaintainer`,
  `sponsorshipsAsSponsor`, `thanks`; organizations swap followers/following for `membersWithRole`;
  repository mode allows `contributors`, `stargazers`, `watchers`, `sponsorshipsAsMaintainer`, `thanks`.
- The alias map is the only place the user-facing names are translated: `followed` to `following`,
  `sponsors` to `sponsorshipsAsMaintainer`, `sponsored` and `sponsoring` to `sponsorshipsAsSponsor`,
  `members` to `membersWithRole`. The order requested by the user is preserved.
- Repository mode takes owner and repo from `data.user.repositories.nodes[0]`, not from the query directly.
- `contributors` uses `rest.repos.listContributors`; `thanks` and the synthetic `sponsorshipsCustom` type use
  one `rest.users.getByUsername` call per handle. Everything else is GraphQL.
- `sponsorshipsCustom` is injected at the front of the type list when `plugin_people_sponsors_custom` is set
  and sponsors are displayed. Its results are merged into `sponsorshipsAsMaintainer`, deduplicated by login,
  and `data.user.sponsorshipsAsMaintainer.totalCount` is adjusted up and then back down so the rendered count
  stays truthful.
- `identicons_hide` filters on `avatarUrl?.includes("&u=")`, which is how a real uploaded avatar is told apart
  from a generated one. `identicons` then rewrites every avatar to `https://github.com/identicons/<login>.png`.
  Combining both keeps only users with real avatars but masks them.
- `shuffle` changes the pagination stop condition to fetch ten times `limit` before shuffling, so it is
  noticeably more expensive in API calls.
- `limit` of `0` means unlimited: the pagination loop condition checks `(limit === 0) || (...)` and the
  `splice` is guarded by `limit > 0`.

### Common Patterns
- Cursor pagination with the cursor interpolated as the whole `after: "..."` argument.
- Account-polymorphic queries: `$account` is substituted with `user` or `organization` and the response is
  destructured as `(await graphql(...))[account]`.
- Avatars are always converted last with `imports.imgb64` inside a `Promise.all`.
