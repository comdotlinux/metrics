# isocalendar

## Purpose
Isometric commit calendar plugin: fetches the GitHub contribution calendar over a 180-day or 1-year window and emits a
ready-made `<svg>` string where each day is drawn as an isometric bar whose height scales with that day's contribution
count. It also returns the current and maximum streak, the busiest day count and the average contributions per day.
`supports: user`, `scopes: public_access`, `category: github`, `index: 0`.

## Key Files
| File | Description |
|------|-------------|
| `index.mjs` | Named-exports `statistics(weeks)` (streaks, `max`, `average`) and `render(weeks, duration)` (the svg), both behaviour-preserving extractions imported by `source/app/metrics/merge.mjs`. Computes a start date (1 year or 180 days back), snaps it back to the preceding Sunday at `00:00:00.000` UTC, then `statistics()` walks the range in **4-week slices** (`to.setUTCHours(+4 * 7 * 24)`), each slice one `queries.isocalendar.calendar` call, pushing `weeks` into a shared calendar. Streaks and the average are computed from the flattened `contributionDays`. The SVG is then assembled by hand. |
| `metadata.yml` | `plugin_isocalendar` and `plugin_isocalendar_duration` (`half-year` default, or `full-year`). |
| `examples.yml` | Four examples: half-year, full-year, and the repository's two multi-account cases (`Multiple accounts`, `Multiple accounts with user ignored`). The last two live here rather than in `core` because every `core` case is skipped by `tests/metrics.test.js` (template compatibility is derived from partial file names and `core` has no partial); both are `prod.skip` and `test.modes: [action]`, and both pass a two-line `token: |` block enabling the whole `MERGED` set. |
| `README.md` | Generated by `npm run build`. Do not hand-edit. |

## Skipped subdirectories
- `queries/` - no AGENTS.md: `setup.mjs` loads every file there as a GraphQL query string. Contents:
  - `calendar.graphql` (op `IsocalendarCalendar`, vars: `$login`, `$from`, `$to`) - `user.contributionsCollection(from, to)`
    aliased to `calendar`, returning `contributionCalendar.weeks.contributionDays { contributionCount, color, date }`.
    `$from`/`$to` are ISO 8601 strings; the plugin sets `$to` to the previous day at `23:59:59.999` so consecutive slices
    never overlap.

## For AI Agents
### Working In This Directory
- The SVG is **hand-written string concatenation, not d3**. Each day is three `<path>` elements (top rhombus plus two
  side faces) translated by `(j * -1.7, j + (1 - ratio) * size)` inside a per-week `translate(i * 1.7, i)`, with two
  `<filter id="brightness1|2">` `feComponentTransfer` blocks darkening the side faces by a linear slope. `size` is `6`
  and the whole group is `scale(4) translate(12, 0)`.
- The `viewBox` height switches on duration: `480x270` for `full-year`, `480x170` for `half-year`, and the root element
  carries an inline `margin-top: -130px`. Changing the bar `size` requires re-checking both viewBoxes.
- Bar height is relative to `reference`, the single highest `contributionCount` in the fetched window, so one outlier day
  flattens the rest of the chart. That is intentional.
- The filter ids (`brightness1`, `brightness2`) are global in the final composed SVG. If another plugin ever emits its
  own filters, collisions are possible.
- **The result carries `weeks` (the raw fetched calendar) next to `{streak, max, average, svg, duration}`**, because
  the multi-account merge sums the secondary accounts' daily counts into it and then recomputes streaks and the svg
  with `statistics()` / `render()`. Do not drop `weeks` from the result, and do not change either export's signature
  without updating `source/app/metrics/merge.mjs` — `weeks` is also what the merged run re-renders from.
- Streak counting resets on any day with zero contributions and counts calendar days, including days before the
  account existed if the window reaches back that far.

### Testing Requirements
- `npx jest --runInBand metrics.test.js -t isocalendar` runs `tests/cases/isocalendar.plugin.yml`, including the two
  multi-account cases (Action mode only), which need `METRICS_TOKEN_WORK` in `tests/secrets.json` to resolve to a
  second mocked login.
- Mock: `tests/mocks/api/github/graphql/isocalendar.calendar.mjs`; the per-token login resolution used by the
  multi-account cases comes from `tests/mocks/api/github/rest/users/getAuthenticated.mjs`.
- The merge rules themselves are covered by `npm run test-merge` (`tests/merge.test.js` + `tests/merge.fixtures.mjs`,
  no Chrome, no network, ~1s), which is the fast way to check a change to `statistics()` or `render()`.
- Templates rendering it: `source/templates/classic/partials/isocalendar.ejs`,
  `source/templates/terminal/partials/isocalendar.ejs`.

### Common Patterns
- Date arithmetic uses the `setUTCHours` overflow trick (`setUTCHours(-180 * 24)`) instead of manual day math; keep
  everything in UTC to avoid drifting a week boundary.
- Standard enable guard and `try {} catch (error) { throw imports.format.error(error) }`.
